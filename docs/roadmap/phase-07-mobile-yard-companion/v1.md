# Phase 7 — Mobile Yard Companion

- Version: v1
- Status: Planned
- Depends on: Phase 6 production command APIs
- Blocks: Phase 9; Phase 8 remains independently gated

Phase 6's [temporary shared-environment plan](../phase-06-supabase-authentication/temporary-validation-plan-v1.md) must prove the versioned command envelope, client mutation IDs, entity versions, private upload intents, site authorization, and idempotent replay contract before this phase begins. Phase 6 remains online-required and must not pre-implement this phase's queues or service worker.

## Objective

Make the existing responsive application installable and dependable for yard work, with cached lookup, camera-first evidence, explicit connectivity state, and safe queued actions when connectivity is unavailable.

## Real-world workflow

1. Install or open TBS Operations on a supported phone and authenticate while online.
2. Cache assigned-site projects, active lots, locations, handling requirements, and recent activity.
3. Search and inspect cached work with or without connectivity.
4. Perform receiving, movement, verification, issue, and photo actions; when offline, review and queue them with an explicit pending state.
5. Reconnect and sync automatically when supported or through the always-available Sync action.
6. Resolve stale-data conflicts from a human-readable conflict inbox.

## Domain and public interfaces

- Add `QueuedMutation`, `QueuedPhoto`, `SyncConflict`, connection/sync status, and cache-manifest interfaces.
- Every queued command carries a UUID client mutation ID, command type/version, authenticated user snapshot, site, created time, entity IDs, entity base versions, and serializable validated payload.
- The server remains authoritative. Successful replay is idempotent; stale versions create conflicts instead of last-write-wins overwrites.

## Data and sync

- Add an App Router manifest, install icons, service-worker registration/update handling, secure service-worker headers, and an offline fallback.
- Preserve Turbopack. Use native service-worker APIs and a small typed IndexedDB queue/cache instead of requiring a webpack-only integration.
- Cache only assigned-site operational data and static application assets; never cache administration or report exports for offline use.
- Store captured photo blobs locally with metadata and retry them after their parent command succeeds.
- Attempt background replay where supported and replay on service-worker startup/foreground reconnect otherwise. Always expose manual Sync.
- Warn about browser storage clearing/pressure and provide a count of pending local-only actions.

## UI requirements

- Use the existing routes and components rather than a separate mobile application.
- Add global offline, pending, syncing, conflict, and update-available indicators that do not obscure operational work.
- Show queued state on affected lots/receipts/issues and prevent conflicting duplicate local actions.
- Add a conflict inbox that describes the local action, server change, and safe choices: refresh/discard or re-enter using current data. Never auto-merge physical quantity/location conflicts.

## Desktop behavior

- Desktop remains fully supported and can inspect pending/conflict state, but offline yard interaction is not its primary layout.
- Do not change existing desktop density or navigation to imitate a phone interface.

## Mobile behavior

- Use 44px-or-larger primary targets, strong sunlight-readable contrast, full-height sheets, sticky actions, camera capture, one-handed navigation, and no hover-only behavior.
- Avoid horizontal tables and clearly distinguish cached, pending, synchronized, and conflicted data.
- Keep primary lookup and handling restrictions usable in airplane/offline mode after preparation.

## Migration and rollback

- Version the mobile IndexedDB cache separately from the Phase 1.3 local-production backup format.
- On service-worker/schema upgrade, preserve pending commands/photos or block activation with recovery/export guidance.
- Rollback unregisters the faulty worker only after preserving pending work and restores the last compatible cache reader.

## Out of scope

Native iOS/Android apps, push notifications, silent physical-data conflict resolution, offline administration, offline reporting, and QR scanning.

## Test plan

- Verify manifest/installability, secure-context requirements, offline shell, worker update, cached lookup, cache expiration, and sign-out data cleanup.
- Test queued receiving, movement, verification, issue, and photo actions; duplicate replay; partial upload failure; reconnect; background-sync absence; manual sync; and conflict resolution.
- Test storage pressure/clearing warnings and preservation across service-worker upgrades.
- Run supported iOS Safari/PWA and Android Chrome/PWA field scenarios in addition to desktop/mobile Playwright and axe checks.

## Acceptance criteria

- Prepared users can find cached project material and handling/location information without connectivity.
- Offline actions are visibly pending and never presented as server-confirmed.
- Replayed commands are idempotent and stale physical data becomes a human-resolved conflict.
- Manual Sync works even when Background Sync is unavailable.
- No queued action or photo is lost during a normal application update.

## Final report requirements

Use the [shared final report](../README.md#shared-final-report), including supported-device/browser matrix, offline/reconnect evidence, conflict examples, worker upgrade results, queued-photo recovery, and confirmation that Phase 8 was not implemented.

## Decision log

- v1: Queue yard actions rather than providing read-only or unrestricted offline-first behavior.
- v1: Native PWA infrastructure preserves the repository's Turbopack build.
- v1: Background Sync is an enhancement; manual/foreground replay is mandatory.
