# Phase 9 — Yard Map

> **Historical version.** Superseded by [Phase 9 v2](v2.md), which uses eight current Lavon Conex locations and a data-driven location count.

- Version: v1
- Status: Planned with entry gate
- Depends on: Phase 7 and a confirmed site diagram/storage naming list
- Blocks: Only map drill-through portions of Phase 10

Phase 6's [temporary shared-environment plan](../phase-06-supabase-authentication/temporary-validation-plan-v1.md) establishes stable site/location UUIDs and assigned-site authorization for this future surface. It must not invent site geometry, new-warehouse locations, or map configuration during Phase 6.

## Objective

Provide an accessible schematic entry point for confirmed storage locations so users can highlight a project, issue, or location and then open the canonical storage workspace.

## Real-world workflow

1. Select an authorized site.
2. Open its map and filter by project, material, issue state, or location type.
3. Review location names and truthful material/project counts.
4. Highlight a location and open its existing Storage Workspace for operational details and actions.
5. Switch to the equivalent accessible list at any time.

## Entry gate

- Obtain a user-confirmed diagram and storage naming list for each site being mapped.
- Confirm which areas are operationally addressable and their adjacency/orientation.
- For Lavon, retain seven numbered Conex containers and include only confirmed outdoor and receiving zones.
- Do not infer dimensions or placement from old prompts, stock images, or aesthetic convenience.

## Domain and public interfaces

- Add versioned `SiteMapConfig`, `MapNode`, normalized schematic geometry, display order, label placement, and links to existing storage-location UUIDs.
- Store map geometry as site configuration, not as inventory state.
- Validate that every map node references one active location and every configured location has a list representation.
- Keep the new warehouse as a separate site and configuration when its layout is confirmed.

## Data and services

- Add map-configuration read ports and derived overlay queries for projects, materials, issues, and package counts.
- Counts must use the same current-lot projections as Storage pages; the map cannot maintain duplicate totals.
- Version configuration changes so historical screenshots/audits can identify the layout version in use.

## UI requirements

- Add `/inventory/map` and activate Yard Map navigation only when at least one confirmed configuration is available.
- Build a data-driven accessible SVG schematic with restrained TBS styling, clear focus, text labels, and a synchronized list.
- The map is an alternate navigation surface; it never replaces Storage lists or pages and contains no map-only operation.

## Desktop behavior

- Support filters, hover and keyboard focus details, project highlighting, issue indicators, counts, and direct storage links.
- Provide zoom only when the confirmed layout requires it; preserve readable labels at common desktop sizes.

## Mobile behavior

- Default to the accessible list with an optional pan/zoom schematic.
- Provide large location targets, no hover dependencies, and the same links/actions available outside the map.

## Migration and rollback

- Map configuration is additive and does not change storage/location identifiers.
- Invalid or missing configuration hides the map entry and leaves canonical Storage intact.
- Rollback selects the prior valid configuration version.

## Out of scope

GIS accuracy, GPS, invented measurements, drag-and-drop administration, live asset tracking, 3D Conex visualization, weather overlays, vehicle tracking, and capacity percentages without verified capacity data.

## Test plan

- Validate config versions, node/location referential integrity, overlay/count parity, filters, empty locations, multiple sites, and invalid-config fallback.
- Test keyboard navigation, screen-reader list equivalence, focus/hover parity, reduced motion, responsive pan/zoom, and drill-through.
- Conduct a field review comparing the schematic and naming to the confirmed site diagram.

## Acceptance criteria

- Every rendered node represents a confirmed location and opens its canonical workspace.
- Map and list counts match Inventory projections exactly.
- All information and actions remain accessible without using the SVG.
- No geographic precision or storage capacity is invented.

## Final report requirements

Use the [shared final report](../README.md#shared-final-report), including the approved source diagram/version, node-to-location validation, count parity, accessible-list evidence, and whether Phase 8 remains gated.
