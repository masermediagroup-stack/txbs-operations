# Phase 6 — Supabase and Authentication

> **Historical version.** Superseded by [Phase 6 implementation plan v4](implementation-plan-v4.md) for current Operator/Tech access and field work.

- Version: v1
- Status: Planned
- Depends on: Phase 5 and a validated local backup
- Blocks: Phase 7

Implementation preparation is governed by the [Temporary Supabase and Vercel Validation Plan v1](temporary-validation-plan-v1.md). That supplement authorizes controlled Supabase password accounts for the disposable test site while deferring Entra; it does not authorize production cutover or weaken the Microsoft Entra acceptance criterion below.

## Objective

Move browser-local operations into secure shared production data with Microsoft Entra sign-in, site-aware authorization, durable private media, idempotent command APIs, and a complete audit trail.

## Real-world workflow

1. A TBS employee signs in with the approved Microsoft tenant.
2. The application loads only sites and operations allowed by membership and role.
3. Existing receiving, movement, verification, issue, and outbound workflows use shared data and authenticated command endpoints.
4. An administrator dry-runs and imports the local backup, resolves validation errors, verifies parity, and performs cutover.
5. Managers and administrators review audit history; unauthorized actions fail without leaking record existence.

## Domain and public interfaces

- Add `Profile`, `SiteMembership`, `Role`, and database `AuditRecord` interfaces.
- Use Operator, Manager, and Administrator roles.
- Operator: read assigned sites and perform receiving, movement, verification, issue, and outbound actions.
- Manager: Operator permissions plus corrections, issue resolution, outbound approval, reports, and exports for assigned sites.
- Administrator: Manager permissions plus all sites, users, roles, locations, imports, and configuration.
- Preserve `actorName` snapshots on historical and new events while adding nullable/authenticated `actorUserId`.

## Database and storage

- Create ordered SQL migrations for sites, locations/positions, projects/aliases, groups/lots, photos, verifications, activities, receipts/lines, movements/lines, outbound batches/lines, issues/comments/transitions, profiles, memberships, idempotency records, and audit records.
- Add foreign keys, checks, unique constraints, entity versions, timestamps, and indexes for the existing search/filter/readiness/report workloads.
- Store media in private Supabase Storage buckets with metadata in Postgres and site/entity-based object paths.
- Enable RLS on every exposed table and `storage.objects`; use membership policies for Operators/Managers and administrator policies for all sites.

## Authentication and application access

- Use Supabase Auth with Microsoft Entra ID restricted to the TBS tenant, PKCE callback handling, `@supabase/ssr`, cookie sessions, and Next.js 16 `proxy.ts` refresh.
- Add `/login`, `/auth/callback`, sign-out, unauthorized, and expired-session flows without public signup.
- Treat proxy checks as optimistic routing only; authorize inside every data-access function and command.
- Replace local adapters with Supabase adapters behind the existing feature ports.
- Add stable authenticated Route Handlers for offline-capable commands. Validate with Zod, check role/site access, require a client mutation ID and entity version, and return structured success, validation, authorization, conflict, and retryable-error responses.
- Never expose a service-role/secret key to browser code.

## Migration and rollback

- Import the Phase 1.3 backup format using dry-run validation, schema-version checks, checksums, referential validation, duplicate detection, and idempotent reruns.
- Preserve UUIDs where valid, historical operator names, null historical user IDs, original timestamps, media metadata, and append-only history.
- Produce before/after counts and checksums for every entity and media object.
- Keep the local database read-only through an agreed verification window. Rollback switches adapters back to local read/write only before production mutations begin; after cutover, use database restore and compensating migrations.

## UI requirements

- Replace the placeholder user identity with the signed-in profile and role.
- Add a site switcher only when a user belongs to more than one site.
- Hide unauthorized navigation for clarity while still enforcing every server boundary.
- Add Administration surfaces for members, site membership, roles, migration dry-run/import, and audit access appropriate to Administrator.

## Desktop behavior

- Provide administration and migration tables with explicit destructive-action confirmation and exportable parity reports.
- Preserve all current operational workspaces and loading/error patterns.

## Mobile behavior

- Keep sign-in and session recovery usable on small screens.
- Do not expose dense user/site administration as a primary yard workflow; operational pages remain the mobile priority.

## Out of scope

Public or anonymous access, customer accounts, self-service signup, cross-company tenancy, custom per-screen permission builders, and offline queuing.

## Test plan

- Test migrations from empty and production-like databases, constraints, indexes, functions, and rollback procedures.
- Test every role/action/site combination at both repository/API and RLS levels, including direct-client denial.
- Test OAuth success/failure, tenant restriction, callback tampering, expired sessions, sign-out, and unauthorized route access.
- Test storage read/upload/delete policies and verify missing SELECT/INSERT policy cases are caught.
- Test idempotent command replay, stale-version conflicts, structured errors, migration dry-run, rerun, count/checksum/media parity, and rollback rehearsal.

## Acceptance criteria

- Only approved Microsoft tenant users can sign in.
- Operators and Managers cannot read or mutate unassigned sites; Administrators can manage all sites.
- Direct database and storage access is protected by RLS, not only UI checks.
- Every local record and photo is migrated with documented parity or an explicitly resolved exception.
- Existing feature ports and user workflows continue without storage-specific UI code.

## Final report requirements

Use the [shared final report](../README.md#shared-final-report), including migration and RLS matrices, OAuth configuration checklist without secrets, parity checksums, rollback rehearsal, production cutover evidence, and confirmation that Phase 7 was not started.

## Decision log

- v1: Microsoft Entra ID restricted to the TBS tenant is the only sign-in method.
- v1: Roles fixed to Operator, Manager, and Administrator.
- v1: Stable Route Handlers are used for operational commands so Phase 7 can replay them safely.
- v1 clarification: UI-facing use cases remain stable, but the relational Supabase implementation must not emulate the current whole-snapshot IndexedDB commit interface.
