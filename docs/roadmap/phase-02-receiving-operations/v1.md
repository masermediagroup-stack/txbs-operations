# Phase 2 — Receiving Operations

- Version: v1
- Status: Planned
- Depends on: Phase 1.3
- Blocks: Phase 3

## Objective

Activate `/inventory/receiving` as the controlled inbound workflow that records arrival evidence, identifies or safely quarantines project ownership, creates physical lots, and assigns initial staging or storage.

## Real-world workflow

1. Start or resume a receiving draft.
2. Enter shipment references and match a project by official name, alias, field label, PO, or job number; explicitly choose Unknown Project when unresolved.
3. Photograph material, shipping documents, damage, and the handwritten project label as applicable.
4. Record one or more material lines with description, package type, known quantity or explicit unknown quantity, condition, handling, and label status.
5. Assign a confirmed receiving/staging or storage location and optional exact position.
6. Review the whole receipt, enter the operator name, and complete atomically.

## Domain and public interfaces

- Add `Receipt`, `ReceiptLine`, receipt identity state, inspection state, and document-photo types.
- Permit a nullable project link only while identity is unresolved.
- Represent unknown quantity explicitly; never translate it to zero.
- Store handwritten label text, `labelApplied`, and optional label photo. Do not generate labels.
- Completing a known-project receipt creates material lots, photo links, an initial verification record, and activity in one transaction.
- Completing an unknown receipt creates an `Unknown Shipment` issue and preserves the original receipt evidence.

## Data and services

- Add receipt draft, completion, duplicate-check, and project-resolution ports and IndexedDB adapters.
- Drafts are durable and resumable. Completion is idempotent through a client mutation ID.
- Receipt numbers and shipping references may warn on duplicates but never silently merge records.
- Resolving an unknown receipt attaches it to a project and creates lots without rewriting its original identity state or evidence.

## UI requirements

- Add Receiving to Inventory navigation only when the workflow is functional.
- Replace the placeholder page with a receiving queue, draft/completed filters, and a guided receiving workspace.
- Show why a project matched and make Unknown Project a deliberate action.
- Reuse project search, location selectors, lot fields, photo capture, validation, and handling components from Phase 1.3.

## Desktop behavior

- Use a reviewable multi-section workspace with a persistent receipt summary and clear draft/completed state.
- Allow efficient multi-line entry without hiding validation or identity warnings.

## Mobile behavior

- Use a one-column, full-height workflow with large package controls, camera capture, sticky Continue/Receive actions, and save-and-resume.
- Clearly state that connectivity/offline queuing is not guaranteed until Phase 7.

## Migration and rollback

- Add the receipt stores through a forward-only local schema migration without changing existing lots.
- A failed completion leaves the draft intact and creates no lots, photos, issues, or partial activity.
- Rollback disables the route and restores the prior schema backup without deleting completed receipt evidence.

## Out of scope

OCR, automatic label recognition, vendor management, procurement synchronization, label printing, QR codes, delivery scheduling, and purchase-order editing.

## Test plan

- Test known, alias-matched, and unknown projects; one and multiple lines; known and unknown quantities; damage and handling capture; label evidence; and staging assignment.
- Test draft reload, duplicate warnings, idempotent completion, failed atomic completion, and later unknown-project resolution.
- Verify created lot totals, activity, photos, and issue links.
- Add responsive Playwright and accessible validation/error-summary coverage.

## Acceptance criteria

- A known shipment can be received into valid lots with complete evidence in one atomic action.
- An unknown shipment remains visible, recoverable, and linked to an issue without fake project data.
- Drafts survive reloads and failures do not create partial inventory.
- The manual handwritten-label process is accurately recorded.

## Final report requirements

Use the [shared final report](../README.md#shared-final-report), including receipt-to-lot transaction evidence, unknown-project resolution results, draft recovery results, and confirmation that Phase 3 was not started.

## Decision log

- v1: Manual label capture retained; no QR or thermal printing.
- v1: Unknown quantity is a first-class state rather than zero.
