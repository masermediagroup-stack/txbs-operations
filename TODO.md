# TBS Operations Master Plan

Last reconciled: 2026-10-15

This is the sole active development plan and checklist. Update this file in place as work is accepted, changed, deferred, or completed. Do not create separate phase plans, wave checklists, or roadmap versions. Implementation reports, audits, runbooks, ADRs, and test artifacts remain evidence and reference material; they do not define current priority.

## How to use the Master Plan

- Work in dependency order. Wave A is the only active implementation and acceptance priority. Preserve the existing Wave B implementation, but do not resume Wave B, Wave C, or later feature work until `A-10` closes Wave A.
- A checked item means the named scope is complete at the status stated. Implementation, technical validation, physical-device acceptance, and production readiness are separate states.
- Every new task receives a stable ID, dependency, measurable completion condition, and source or decision reference. Update an existing task when its scope changes instead of creating another planning document.
- Do not mark a task complete from code presence alone. Link its implementation report or test evidence and record remaining acceptance separately.
- The current repository, database migrations, `CONTEXT.md`, ADRs, and implementation evidence override historical wording when they conflict.
- Detailed GitHub issues carry the specification, behavior slices, blockers, and validation; this file retains stable IDs and controls priority/status. Follow `docs/agents/issue-tracker.md`. Publish technical requirements with synthetic examples because the repository is public; keep company source files and restricted evidence in approved private storage.

Status terms used below: **Outstanding**, **In progress**, **Implemented; acceptance pending**, **Completed with evidence**, **Gated**, **Deferred production gate**, **Superseded**, and **Explicitly excluded**.
